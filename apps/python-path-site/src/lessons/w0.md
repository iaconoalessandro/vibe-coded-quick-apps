## Why this week exists
A notebook remembers whatever cells you ran, in whatever order you ran them. Run cell 5, edit cell 2, rerun cell 7, and the result depends on history nobody can see. That is why courses, exams and companies want **scripts**. A `.py` file runs top to bottom, the same way every time. It can be imported, tested, put in git, reviewed, and scheduled on a server. Your DSS scripts will run against a database for minutes at a time, so they have to be scripts.

This week is pure setup. It's boring, and it's the foundation of everything else.

## The mental model
```text
Terminal ──runs──▶ python (from .venv) ──reads──▶ exercises/w00_setup.py
   │                         ▲
   └── pytest ── imports ────┘      git ── snapshots ──▶ GitHub
```
- **Terminal**: a text way to drive the computer. You're always *in* a folder (`pwd`), and relative paths start there.
- **Interpreter**: `python file.py` reads the file top to bottom and executes it. `import x` runs `x.py` once and gives you its names.
- **Virtual environment**: a private Python + packages per project, in `.venv/`. Activate it in every new terminal, and check with `which python`.
- **pytest**: finds `tests/test_*.py`, runs every `test_*` function, and reports which `assert`s failed. Red, then code, then green.
- **git**: saves snapshots of your folder. `add` chooses what goes in the snapshot, `commit` takes it, `push` copies it to GitHub.

## Reading a traceback
```text
Traceback (most recent call last):
  File ".../tests/test_w00_setup.py", line 24, in test_average_of_positive_no_positives
    assert average_of_positive([]) == 0.0
  File ".../exercises/w00_setup.py", line 54, in average_of_positive
    return total / count
ZeroDivisionError: division by zero
```
Read it **bottom-up**. The last line is *what* went wrong. The line above it is *where*, and here that's your file, line 54. Everything above that is *how you got there*. Ignore frames inside Python's own libraries and look for the first frame in **your** files.

## The debugger beats print()
In VS Code, click left of a line number to set a red-dot breakpoint, then **Run › Start Debugging** (F5). Execution stops there. Hover over variables, or watch them in the left panel. F10 runs one line, F11 steps into a function call. You'll use this all the way through the DSS project.

> **Remember**
> - New terminal? `source .venv/bin/activate`, then `which python`.
> - Read tracebacks from the bottom. Find the first line that is your code.
> - `git status` before every commit. `.venv/`, `.env` and data files never go in git.
> - A test is just a function with `assert`. Never edit a test to make it pass.
