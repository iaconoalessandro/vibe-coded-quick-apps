## What this week is for
By the end of this week you will have a working setup: a terminal you can find your way around, a project folder with its own Python, a test you can run, a debugger you can step through, and the whole thing saved on GitHub. There is very little Python in it. Everything after this week assumes these tools work, so it is worth doing slowly and properly.

You will write Python in **`.py` files** (scripts), not in Jupyter notebooks. A notebook remembers whatever cells you ran, in whatever order you ran them: run cell 5, edit cell 2, rerun cell 7, and the result depends on a history nobody else can see. A `.py` file runs from the first line to the last, the same way every time, on any computer. That is why it can be tested, saved in git, reviewed by someone else and run on a server. The DSS project scripts run for minutes against a real database, so they have to be scripts.

## The pieces and how they fit
```text
Terminal ──runs──▶ python (from .venv) ──reads──▶ exercises/w00_setup.py
   │                         ▲
   └── pytest ── imports ────┘      git ── snapshots ──▶ GitHub
```
You type commands in the **terminal**. One of those commands starts **Python**, which reads your file and runs it. Another starts **pytest**, which loads your file and checks that your functions give the right answers. **git** keeps a history of your folder, and **GitHub** keeps a copy of that history online. The sections below take these one at a time.

## The terminal
The terminal is a window where you control the computer by typing instead of clicking. On a Mac it's the *Terminal* app (or the terminal panel inside VS Code: **View › Terminal**). On Windows, use *PowerShell* or the VS Code terminal.

The most important idea: **the terminal is always "standing" inside one folder**, called the *current directory*. Every relative path you type starts from there. These are the commands you need this week:

| Command | What it does | Example |
|---|---|---|
| `pwd` | prints the folder you're in ("print working directory") | `/Users/ada/code` |
| `ls` | lists what's in it (`dir` on Windows) | `exercises  tests  README.md` |
| `cd name` | moves into a folder | `cd python-path` |
| `cd ..` | moves up one folder | |
| `cd ~` | goes to your home folder | |

Try it: open a terminal, run `pwd`, then `ls`, then `cd` into a folder you saw, then `pwd` again. If a command says *No such file or directory*, you're almost always in the wrong folder: run `pwd` and check.

Two keys save a lot of typing: **Tab** completes a file or folder name, and the **up arrow** brings back your previous command.

## Running a Python file
A `.py` file is just text. Create `hello.py` containing one line:
```python
print("Hello from a script")
```
and run it from the terminal, in the folder that contains it:
```bash
python hello.py
```
Python reads the file from top to bottom and runs each line. `print(...)` writes text to the terminal, so you see `Hello from a script`. If you see `can't open file 'hello.py'`, you're not in the folder that contains it.

On a Mac the command may be `python3` until you activate a virtual environment (next section). After activating, plain `python` works.

## Virtual environments: one private Python per project
Python projects use extra packages (pytest this week, pyodbc later). If you install them all into one shared Python, projects end up needing different versions of the same package and break each other. A **virtual environment** (venv) is a private folder, `.venv/`, holding a copy of Python and only this project's packages.

You create it once per project:
```bash
cd ~/code/python-path
python3 -m venv .venv               # create the .venv folder
```
and **activate** it every time you open a new terminal:
```bash
source .venv/bin/activate           # Mac/Linux
.venv\Scripts\Activate.ps1          # Windows PowerShell
```
Activation changes one thing: when you type `python` or `pip`, the terminal now uses the ones inside `.venv`. Your prompt shows `(.venv)` at the start, and you can check:
```bash
which python                        # should end in /python-path/.venv/bin/python
```
Now install packages *into* the venv:
```bash
python -m pip install pytest
```
Writing `python -m pip` instead of plain `pip` guarantees that pip installs into the same Python you'll run.

Finally tell VS Code to use it: **Cmd+Shift+P › Python: Select Interpreter**, then pick the one in `.venv`.

**Common trap:** you open a new terminal tab, forget to activate, and suddenly "pytest is not installed" or a test about the venv fails. The fix is always the same: `source .venv/bin/activate`.

## Functions and tests, the smallest possible version
Every exercise on this site is a **function**: a named piece of code that takes inputs and gives back a result. You'll learn functions properly in week 1. For now, read this one:
```python
def double(x):          # "def" starts a function called double, with one input x
    return x * 2        # "return" hands the result back
```
`double(5)` gives back `10`. The indented lines belong to the function.

A **test** is another function that calls yours and checks the answer with `assert`:
```python
def test_double():
    assert double(5) == 10      # == asks "are these equal?"
    assert double(0) == 0
```
`assert something` does nothing when `something` is true, and stops with an error when it's false. **pytest** finds every file named `test_*.py` in `tests/`, runs every function named `test_*`, and prints a report: a green dot for each passing test, and an explanation for each failing one.

In the exercise files, each function starts as a *stub*: the description is written, and the body is `raise NotImplementedError`, which means "not written yet". So the first time you run the tests, everything fails. That's on purpose. The daily loop is:

1. Run the tests and see red: `pytest tests/test_w00_setup.py`
2. Read the description of one function, and replace `raise NotImplementedError` with your code.
3. Run the tests again. Repeat until that function's test is green.

To run only the tests whose name contains a word, add `-k`: `pytest tests/test_w00_setup.py -k hello`. Add `-v` to see one line per test.

Never change a test to make it pass. The test is the specification: if it disagrees with your code, your code is wrong (or you've misread the task).

## Reading a traceback
When Python hits an error it prints a **traceback**: the list of function calls that were running when it crashed.
```text
Traceback (most recent call last):
  File ".../tests/test_w00_setup.py", line 24, in test_average_of_positive_no_positives
    assert average_of_positive([]) == 0.0
  File ".../exercises/w00_setup.py", line 54, in average_of_positive
    return total / count
ZeroDivisionError: division by zero
```
Read it **from the bottom up**:

- The **last line** says *what* went wrong: `ZeroDivisionError: division by zero`.
- The frame just above says *where*: `w00_setup.py`, line 54, the line `return total / count`.
- The frames above that say *how you got there*: the test on line 24 called your function with `[]`, an empty list.

Put those together and you have the bug: with an empty list, `count` is 0, and you divide by it. Frames inside Python's own libraries (paths containing `site-packages` or `lib/python3`) are almost never where the bug is; look for the first frame in **your** files.

## The debugger: watching your code run
`print()` shows you one value at one moment. A **debugger** pauses the program on a line you choose and lets you look at every variable, then move forward one line at a time.

In VS Code:

1. Open the file and click in the margin to the left of a line number. A red dot appears: that's a **breakpoint**.
2. Open the Testing panel (the flask icon) and click the debug icon next to a test, or use **Run › Start Debugging** (F5) on a script.
3. Execution stops at the red dot. The **Variables** panel on the left shows every variable and its current value. Hovering over a name in the code shows it too.
4. Press **F10** ("step over") to run one line and stop again. Watch the variables change. **F11** ("step into") goes inside a function call. **F5** continues to the next breakpoint.

The exercise `average_of_positive` has three planted bugs. Don't stare at the code trying to spot them. Put a breakpoint on the `for` line, step through with the input `[2, -1, 4]`, and after each step ask: "is `total` what I expect? is `count`?" The moment a value surprises you, you've found a bug.

## git and GitHub: saving snapshots
**git** records snapshots (called *commits*) of your project folder, so you can see what changed, when, and go back. Three commands do most of the work:
```bash
git status                     # what changed since the last snapshot?
git add exercises/w00_setup.py # choose what goes into the next snapshot (the "staging area")
git commit -m "Week 0: hello and python_version"   # take the snapshot, with a message
```
`add` copies the file *as it is now* into the staging area. If you edit it again after `add`, `git status` shows it as modified again, and you need another `add` for the new version to be included.

Once, at the start of a project:
```bash
git init                       # turn the folder into a repository
```
**GitHub** is a website that stores a copy of your repository. With the GitHub command line tool:
```bash
gh auth login                  # once per computer
gh repo create python-path --private --source=. --push   # create the online copy and upload
git push                       # afterwards: upload new commits
```
Some files must **never** be committed: `.venv/` (thousands of machine-specific files; anyone can rebuild it), `.env` (passwords), and large data files. The repository's `.gitignore` file lists them so git ignores them. Run `git status` before every commit and read what's about to go in.
