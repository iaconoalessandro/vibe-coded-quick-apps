## What this week is for
Until now you've called your functions from tests. A grader, a teammate or a server will instead **run your script from the terminal**, often on different data and without reading your code. This week turns a collection of functions into a proper **program**: it takes options on the command line, reports what it's doing through logging, signals success or failure with an exit code, and can be both run and imported. Then you use it to run the whole DSS Part 1 pipeline end to end from a clean copy of your repository.

## How a program gets its inputs: command-line arguments
When you type
```bash
python sales2star.py data/sales.arff --out-dir out -v
```
everything after the script name reaches Python as a list of strings, `sys.argv`:
```python
import sys
print(sys.argv)     # ['sales2star.py', 'data/sales.arff', '--out-dir', 'out', '-v']
```
You could pick that list apart by hand, but you'd have to handle missing values, wrong types, `--help`, and options in any order. The standard library's **argparse** does all of that from a description of what you accept:
```python
import argparse
from pathlib import Path

parser = argparse.ArgumentParser(prog="sales2star", description="Turn sales data into a star schema.")
parser.add_argument("input", type=Path, help="the input file")                  # positional: required
parser.add_argument("--out-dir", type=Path, default=Path("out"), help="output folder")
parser.add_argument("--limit", type=int, default=None, help="stop after N rows")
parser.add_argument("--dry-run", action="store_true", help="compute, write nothing")
parser.add_argument("-v", "--verbose", action="count", default=0, help="-v, -vv for more detail")

args = parser.parse_args(["data.arff", "--limit", "50", "-vv"])
args.input, args.out_dir, args.limit, args.dry_run, args.verbose
# (Path('data.arff'), Path('out'), 50, False, 2)
```
What each part does:

- A name without dashes (`"input"`) is a **positional** argument: required, identified by its position.
- A name with dashes (`"--out-dir"`) is an **option**: optional, with a `default`. In `args` the dashes become underscores: `args.out_dir`.
- `type=int` converts the string for you, and if the user types `--limit many`, argparse prints a clear error and exits. You never write that check yourself.
- `action="store_true"` makes a **flag**: present means `True`, absent means `False`.
- `action="count"` counts repetitions: `-v` is 1, `-vv` is 2.
- `help=` text appears when someone runs `python sales2star.py --help`, which argparse builds for free.

`parse_args()` with no argument reads `sys.argv`. Passing a list explicitly, as above, is how tests check your parser without a terminal.

## Logging instead of print
A running program has two kinds of output. Its **result** (the data it produces) and a **story** about what it's doing: "read 21 rows", "skipped 3 bad dates", "wrote 4 tables". `print` mixes both into the same stream. The `logging` module handles the story, with **levels** that say how important each message is:

| Level | Use for |
|---|---|
| `DEBUG` | details you want only when hunting a bug |
| `INFO` | normal progress: counts, file names, timings |
| `WARNING` | something odd that the program worked around |
| `ERROR` | something failed |

```python
import logging
log = logging.getLogger(__name__)          # one logger per module, named after it

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
log.debug("row 17: %s", row)               # hidden: below INFO
log.info("read %d rows from %s", 21, "sales.arff")
log.warning("3 rows with bad dates skipped")
```
```text
INFO read 21 rows from sales.arff
WARNING 3 rows with bad dates skipped
```
Only messages at or above the configured level appear. The default level is **WARNING**, which is why `log.info(...)` seems to do nothing until you configure logging. Connecting the level to `-v` gives users control without touching the code: no flag shows warnings and errors, `-v` adds INFO, `-vv` adds DEBUG.

Notice `log.info("read %d rows", n)` rather than an f-string: logging fills in the values only if the message is actually shown. Log messages go to **stderr**, a separate stream from the result on stdout, so `python script.py > result.txt` captures only the result.

## Exit codes: telling the shell how it went
Every program ends with a number, its **exit code**. `0` means success; anything else means failure. Shell scripts, schedulers and CI systems read it to decide what happens next. In the terminal, `echo $?` shows the last command's exit code.

In Python, `sys.exit(code)` ends the program with that code. The clean pattern is a `main` function that **returns** the code, and one line that passes it to `sys.exit`:
```python
def main(argv=None):
    args = build_parser().parse_args(argv)
    logging.basicConfig(level=..., format="%(levelname)s %(message)s")
    if not args.input.exists():
        log.error("input file not found: %s", args.input)
        return 1                          # failure, with a message that says why
    ...                                   # the actual work, in small steps, each logged
    return 0                              # success

if __name__ == "__main__":
    sys.exit(main())
```
Why `main(argv=None)`? Run from the terminal, `argv` is `None`, so argparse reads `sys.argv`. From a test, you call `main(["data.arff", "--dry-run"])` and check the returned code, without starting a new process.

And why `if __name__ == "__main__":`? (Week 4 introduced it.) Importing a module runs its whole file. This line makes `main()` run only when the file is executed as a program, so tests and other modules can import its functions safely.

You can also run a module inside a package with `python -m package.module`, which is how the week-6 exercise runs: `python -m exercises.w06_cli practice_data/sales.arff -v`.

## Never crash on an edge case, never fake a number
Analytical code divides constantly: averages, ratios, percentage changes. Division by zero will happen in real data (a user with no daytime posts, a category with no posts last month). There are three possible behaviours, and only one is right:

- **Crash** (`ZeroDivisionError`): one odd user stops the whole pipeline.
- **Return 0**: looks like a real result, and silently drags averages down. This is the dangerous one.
- **Return `None`** (or `NULL` in SQL): "not defined". It shows up as missing, gets excluded from averages, and you can count how often it happened.

Return `None`, and write in your report how many cases there were and why.
```python
def share(part, whole):
    if not whole:              # catches 0 and None
        return None
    return part / whole
```
Percentage change from `old` to `new` is `(new - old) / old * 100`: from 80 to 100 is +25%, from 100 to 80 is −20% (not −25%: the base is different). It's undefined when `old` is 0.

## Checking SSIS results with Python
DSS Assignments 8–11 are done in SSIS, a visual tool where mistakes are easy to make and hard to see. You can **verify** them independently: export a small slice of the fact table, compute the same metric with your own week-2 grouping code, and compare. If the numbers differ, one of the two is wrong, and you'll find out before the grader does. Typical edge cases to decide and document: division by zero, a user with a single post (no standard deviation), values exactly on a threshold (is "more than one std" `>` or `>=`?).

## The clean-clone test
Your code works on your computer. Does it work anywhere else? The only way to know is to try it as a stranger would: clone the repository into an empty folder, install from `requirements.txt`, and run the README's commands exactly as written.
```bash
cd /tmp && git clone <your repository url> test-clone && cd test-clone
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
python src/split_tables.py data/input.arff --out-dir out -v
```
Typical failures this reveals: a path hard-coded as `/Users/yourname/...`, a package installed on your machine but missing from `requirements.txt`, a data file that never went in the repository, a step that only worked because of something you ran by hand. If it fails here, it fails for the grader.

`requirements.txt` lists the packages your project needs, one per line (`pyodbc==5.2.0`). `python -m pip freeze` shows what's installed in your venv.

## Try it yourself
1. Write a script `greet.py` that takes a name (positional) and `--times N` (default 1) and prints the greeting N times. Run it with `--help`.
2. Run it with `--times many`. What does argparse print? What's the exit code (`echo $?`)?
3. Add logging: an INFO line at the start. Run with and without `-v`.
4. Make the script return exit code 2 when the name is empty. Check with `echo $?`.
5. Import `greet` from another file. Does the greeting print on import? Why not?

> **Remember**
> - argparse turns `sys.argv` into typed, documented options; `--help` comes free.
> - `print` is the program's output; `logging` is its story. Default level is WARNING.
> - `main(argv=None)` returns an exit code: 0 for success, anything else for failure.
> - Undefined results are `None`, never a fake 0. Count and document them.
> - Pass paths as arguments. Never hard-code `/Users/...`.
> - If the clean clone fails, it fails for the grader.
