## From star schema to cube
In weeks 4 and 5 you built a star schema: a fact table of events, with dimension tables around it. You can answer any question with SQL, but each question means writing joins and group-bys again. A **cube** (built in SSAS, SQL Server Analysis Services) sits on top of the star schema and **pre-organises** it for analysis: you declare once which dimensions exist, how they break down into levels, and which numbers can be added up. After that, tools like Excel, Power BI and the MDX language (next week) can slice the data any way without writing SQL.

The mental picture: a spreadsheet has two axes (rows and columns). A cube has as many axes as you have dimensions: date, store, title... Each **cell** sits at one combination of positions, one per dimension, and holds the measures for that combination: "quantity sold, for store 7131, title PS2091, in September 1994".

## The three things you define
### Dimensions and attributes
Each dimension table becomes a cube **dimension**. Its columns become **attributes**: the things you can filter or group by. If a question needs "season", season must be an attribute of the date dimension. If it isn't, you have to go back and add the column to the table, reload, and rebuild. So, **before building the cube, read the Part 2 queries and list every attribute they use.**

### Hierarchies
A **hierarchy** is a drill-down path through attributes, from coarse to fine:
```text
Date:          Year → Quarter → Month → Day
Time of day:   Day part (night/morning/...) → Hour
Geography:     Country → Region → City
```
With a hierarchy, a user looking at yearly totals can open one year to see its quarters, then a quarter to see its months. Each level must fit entirely inside the level above: every month belongs to exactly one quarter. (A "month" attribute that's just 1–12 doesn't fit inside a year by itself: January 1994 and January 1995 are different members, so month keys usually include the year.)

### Measures
**Measures** come from the numeric columns of the fact table, with an aggregation: sum of likes, count of events, maximum of something. Ask for each one: does adding it up make sense? Quantities and counts add up across every dimension. Some numbers don't: an average, or a "number of followers" snapshot, gives nonsense when summed. Those need a different aggregation or a calculated measure (next week).

**Distinct counts** need care. "How many different users posted?" can't be computed by adding the counts of each day, because a user active on two days would count twice. SSAS needs a separate **distinct count measure** for that.

Add only the measures the queries actually need. A smaller cube is easier to check.

## Checking the cube
Process the cube, then compare a few numbers with SQL on the star schema: the grand total of each measure, the total for one year, the count for one store. If the cube and SQL disagree, the usual suspects are a wrong key relationship between a dimension and the fact table, or facts whose keys don't exist in the dimension.
