## Iterators and generators: data that flows
Before databases, one Python idea you need to load big files efficiently.

When you write `for line in f`, the file doesn't hand over all its lines at once. It gives one line each time the loop asks for the next. Anything that works this way is an **iterator**. Lists are different: all their items exist in memory at the same time.

You can write your own iterator with a **generator function**: a function that uses `yield` instead of `return`.
```python
def countdown(n):
    while n > 0:
        yield n          # hand over one value, then PAUSE here
        n -= 1

for x in countdown(3):
    print(x)             # 3, 2, 1
```
Calling `countdown(3)` doesn't run the body. It creates a generator object. Each time the `for` loop asks for the next value, the function runs until the next `yield`, hands over that value, and pauses, keeping all its variables, until it's asked again. When the function ends, the loop ends.
```python
>>> g = countdown(2)
>>> next(g)              # next() asks for one value by hand
2
>>> next(g)
1
>>> next(g)
StopIteration            # nothing left
```
Why bother? Because a generator **holds one item at a time**. A generator that reads a 10 GB CSV yields one row, you process it, the row is forgotten, the next one arrives. Memory stays tiny.
```python
import csv
def read_rows(path):
    with open(path, encoding="utf-8", newline="") as f:
        yield from csv.DictReader(f)     # yield each row the reader produces
```
`yield from x` means "yield every item of x, one by one".

A **generator expression** is the lazy cousin of a list comprehension, with round brackets: `(r["qty"] for r in rows)`. `sum(int(r["qty"]) for r in read_rows(p))` adds up a column of a file of any size without ever building a list.

One catch: a generator can be consumed **only once**. After you've looped over it, it's empty:
```python
g = (x * 2 for x in range(3))
list(g)     # [0, 2, 4]
list(g)     # []
```
### Batches
Databases prefer receiving rows in groups (say 1,000 at a time) rather than one by one or all at once. So a common helper takes any iterable and yields lists of up to `n` items: collect items into a list; when it reaches `n`, yield it and start a new one; at the end, yield whatever is left over. That's the first exercise this week.

## Talking to a database: the DB-API
Every Python database library follows the same steps:
```python
import sqlite3

conn = sqlite3.connect("shop.db")     # 1. connect (":memory:" for a throwaway database)
cur = conn.cursor()                    # 2. get a cursor: the thing that runs statements

cur.execute("CREATE TABLE item (id INTEGER PRIMARY KEY, name TEXT, price REAL)")    # 3. run SQL
cur.execute("INSERT INTO item (id, name, price) VALUES (?, ?, ?)", (1, "pen", 1.5))
conn.commit()                          # 4. make the changes permanent

cur.execute("SELECT name, price FROM item WHERE price > ?", (1.0,))
cur.fetchall()                         # 5. fetch results: [('pen', 1.5)]
conn.close()
```
Step by step:

- **connect** opens the database. For SQL Server it's `pyodbc.connect(connection_string)`; everything after is the same.
- **cursor** runs statements and holds the results of the last query.
- **execute** runs one SQL statement. The `?` marks are **placeholders**; the values go in a separate tuple (note the comma in `(1.0,)`: a one-item tuple).
- **commit** saves. Changes are made inside a **transaction**, which is only written permanently when you commit. If you close without committing, everything since the last commit is thrown away. That's a feature: if your script crashes halfway through a load, the database isn't left half-updated.
- **fetchall** returns every result row as a list of tuples; **fetchone** returns one row; **fetchmany(n)** returns the next `n`.

`conn.execute(...)` is a shortcut that makes a cursor for you, handy for one-off statements. `conn.executescript("...; ...;")` runs several statements in one go (SQLite only), useful for creating a schema.

### Why placeholders, never f-strings
It's tempting to build SQL with an f-string:
```python
name = "O'Brien"
cur.execute(f"INSERT INTO person VALUES ('{name}')")
# INSERT INTO person VALUES ('O'Brien')   <- the apostrophe ends the string: syntax error
```
Worse, if `name` came from a file and contained `x'); DROP TABLE person; --`, the database would run that too. This is **SQL injection**, one of the most common security holes in real software. With placeholders, the driver sends values separately from the SQL text, so a value can never be mistaken for code:
```python
cur.execute("INSERT INTO person VALUES (?)", (name,))      # always safe
```
Placeholders work for **values only**, not for table or column names. If a name comes from data, check it yourself: `"fact_sales".isidentifier()` is `True`, `"t; DROP TABLE t".isidentifier()` is `False`.

### Inserting many rows
`executemany` runs one statement for every tuple in a list:
```python
rows = [(2, "ink", 3.0), (3, "pad", 2.2)]
cur.executemany("INSERT INTO item (id, name, price) VALUES (?, ?, ?)", rows)
conn.commit()
```
Combined with batches and a generator, this loads a file of any size with flat memory:
```python
for batch in batched(read_rows(path), 1000):
    cur.executemany(sql, [(r["id"], r["name"], r["price"]) for r in batch])
conn.commit()
```

## Measure the speed, don't guess
How you insert makes an enormous difference. Try it: insert 100,000 rows into SQLite three ways, timing each with `time.perf_counter()`:

1. `execute` and `commit` for every row;
2. `execute` for every row, one `commit` at the end;
3. `executemany` in batches of 5,000, one `commit` at the end.
```python
import time
t0 = time.perf_counter()
...                                  # the code you're timing
print(f"{time.perf_counter() - t0:.2f} s")
```
Expect differences of 10 to 100 times. Committing is expensive because it forces a write to disk, and each round trip to a database server costs network time. Keep the table of numbers: it's the "efficiency" paragraph of the DSS report, backed by evidence.

## Loading a star schema: order matters
The fact table refers to the dimensions through foreign keys. If a fact row says `store_key = 3`, store 3 must already exist. So load **dimensions first, then facts**. Loading the other way round either fails (when the database enforces the keys) or leaves the database in a broken state in between.

Creating the tables in a script that can be re-run safely is common practice: drop them if they exist, then create them. Drop the fact table first, because it depends on the others.

SQLite is flexible with types: if a column is declared `INTEGER` and you insert the string `"5"`, it stores the number 5. SQL Server is stricter, so convert values in Python before inserting.

## Querying from Python
Once loaded, ask questions in SQL and get Python tuples back. A join plus a group-by, for example "total quantity per store, largest first":
```sql
SELECT s.stor_id, SUM(f.qty) AS total
FROM fact_sales f
JOIN dim_store s ON s.store_key = f.store_key
GROUP BY s.stor_id
ORDER BY total DESC, s.stor_id
```
Read it in the order the database works: take `fact_sales`, attach each row's store via the key (**JOIN**), put rows with the same store together (**GROUP BY**), add up `qty` in each group (**SUM**), then sort (**ORDER BY**), with `stor_id` breaking ties so the result is always in the same order.

Triple-quoted strings let you write SQL over several lines in Python, which is much easier to read.

## Exporting results to JSON, without running out of memory
To export a large query result, don't `fetchall()` it: that loads every row at once. Fetch in chunks with `fetchmany`, and write as you go. Column names are in `cur.description`, a tuple per column whose first item is the name:
```python
cur = conn.execute("SELECT id, name FROM item")
names = [d[0] for d in cur.description]          # ['id', 'name']
while True:
    chunk = cur.fetchmany(1000)
    if not chunk:                                # empty list: no more rows
        break
    for values in chunk:
        record = dict(zip(names, values))        # {'id': 1, 'name': 'pen'}
        ...
```
`zip(a, b)` pairs items by position: `zip(["id", "name"], (1, "pen"))` gives `("id", 1), ("name", "pen")`, and `dict(...)` turns those pairs into a dict.

`json.dump(all_rows, f)` needs the whole list in memory, so for a streaming export you write the JSON array yourself: `[`, then each record with `json.dumps(record)` separated by commas, then `]`.

## Credentials stay out of the code
Database passwords must never be written in your scripts or committed to git: repositories get shared, copied and published. Keep them in **environment variables**, which a program reads at run time:
```python
import os
server = os.environ["DB_SERVER"]        # KeyError if it's not set
```
You set them in the terminal (`export DB_SERVER=...`) or in a `.env` file that is listed in `.gitignore`. When something is missing, fail with a message that lists **everything** missing at once, so the user can fix it in one go.

## SQL Server from your computer
On the university network (VPN on), with Microsoft's ODBC driver installed:
```bash
brew tap microsoft/mssql-release https://github.com/Microsoft/homebrew-mssql-release
HOMEBREW_ACCEPT_EULA=Y brew install msodbcsql18
python -m pip install pyodbc
```
```python
import os, pyodbc
conn = pyodbc.connect(
    "DRIVER={ODBC Driver 18 for SQL Server};"
    f"SERVER={os.environ['DB_SERVER']};DATABASE={os.environ['DB_NAME']};"
    f"UID={os.environ['DB_USER']};PWD={os.environ['DB_PASSWORD']};TrustServerCertificate=yes"
)
cur = conn.cursor()
cur.fast_executemany = True              # without it, executemany sends rows one by one
print(cur.execute("SELECT @@VERSION").fetchone()[0])
```
`fast_executemany = True` makes pyodbc send a whole batch in one round trip; without it, inserting a large table over the VPN can take hours. If the Mac driver gives trouble, run the same script inside a Windows VM: the Python doesn't change.
