## What this week is for
So far your data lived inside your code. Real data lives in **files**, in several formats, and is often messy or too large to load at once. This week you learn to read and write text files, CSV, JSON and XML, to parse the ARFF format used by Weka, and to handle the errors that real files cause.

One design rule ties it together: **every reader returns the same shape**, a list of dicts (or later, a stream of dicts). Then the rest of your program never has to care whether the data came from a CSV or an XML file. DSS Assignment 1 hands you four formats at once, which is exactly why this matters.

## Paths: telling Python where a file is
A **path** is a file's address. It can be **absolute**, starting from the top of the disk (`/Users/ada/code/python-path/practice_data/jobs.csv`), or **relative**, starting from the folder the terminal is in (`practice_data/jobs.csv`). Relative paths are what you want in code, so that it works on other people's computers, but they only work if you run the program from the right folder.

The `pathlib` module gives you `Path` objects, which join parts correctly on every operating system:
```python
from pathlib import Path

data = Path("practice_data")
path = data / "jobs.csv"            # / joins path parts
path.name, path.suffix, path.stem   # ('jobs.csv', '.csv', 'jobs')
path.exists()                       # True or False
path.parent                         # Path('practice_data')
Path("out/star").mkdir(parents=True, exist_ok=True)   # create folders, no error if they exist
sorted(data.glob("*.csv"))          # every .csv file in the folder
```

## Opening, reading and writing text files
```python
with open(path, encoding="utf-8") as f:
    for line in f:
        print(line.rstrip("\n"))
```
Line by line:

- `open(...)` connects to the file and gives you a **file object**, here named `f`.
- `encoding="utf-8"` says how bytes on disk become characters. If you leave it out, Python uses the computer's default, which differs between Mac and Windows: the same code then reads "è" correctly on one machine and as garbage on another. Always write it.
- `with ... as f:` guarantees the file is **closed** when the indented block ends, even if an error happens inside. Open files hold system resources; forgetting to close them causes subtle bugs.
- `for line in f` reads **one line at a time**. Each `line` still ends with the newline character `"\n"`, which is why we strip it.

Reading line by line uses the same small amount of memory whether the file is 1 KB or 10 GB. The alternative, `f.read()`, loads the whole file into one string: fine for small files, a crash for big ones.

Writing:
```python
with open("out/notes.txt", "w", encoding="utf-8") as f:   # "w" = write (replaces the file!)
    f.write("first line\n")                               # you add the newlines yourself
    f.write("second line\n")
```
Use `"a"` instead of `"w"` to append to the end of an existing file.

## CSV: comma-separated values
A CSV file is a table as text: one row per line, values separated by commas, usually with a header line of column names.
```text
id,name,qty
7066,"Rossi, Mario",5
7067,Bianchi,12
```
It looks as if `line.split(",")` would be enough. It isn't:
```python
>>> '7066,"Rossi, Mario",5'.split(",")
['7066', '"Rossi', ' Mario"', '5']          # the name was cut in two
```
When a value contains a comma, CSV wraps it in quotes, and a value containing a quote doubles it. The `csv` module knows all these rules. Use it, always:
```python
import csv

with open("people.csv", encoding="utf-8", newline="") as f:
    reader = csv.DictReader(f)          # reads the header, then one dict per row
    for row in reader:
        print(row)                      # {'id': '7066', 'name': 'Rossi, Mario', 'qty': '5'}
```
Two details:

- `newline=""` lets the csv module handle line endings itself (some values may legally contain newlines). Use it for every CSV file, reading or writing.
- **Every value is a string**, even `'5'`. `row["qty"] + 1` raises `TypeError`. Convert on purpose: `int(row["qty"])`.

If the file has no header line, give the column names yourself: `csv.DictReader(f, fieldnames=["id", "name", "qty"])`.

Writing a list of dicts:
```python
rows = [{"id": 1, "name": "Rossi, Mario"}, {"id": 2, "name": "Bianchi"}]
with open("out.csv", "w", encoding="utf-8", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["id", "name"])
    writer.writeheader()
    writer.writerows(rows)              # adds the quotes around "Rossi, Mario" for you
```

## Missing values and type conversion
Real files have holes. A missing value might be an empty string `""`, a question mark `"?"` (the ARFF convention), `"NA"`, or a space. Decide once what counts as missing and turn it into `None`, so the rest of your code has one thing to check.

Converting strings to numbers is a good place to learn the "try it and see" style that Python prefers:
```python
def parse_amount(text):
    text = text.strip()
    if text in {"", "?"}:
        return None
    try:
        return float(text)
    except ValueError:              # not a number after all
        return None
```
Instead of checking in advance whether `text` "looks like" a number (signs, decimals, exponents: easy to get wrong), you simply try to convert it and handle the failure. The next section explains `try` properly.

## Exceptions: when things go wrong
An **exception** is Python's way of saying "I can't do this": `ValueError` (right type, bad value: `int("abc")`), `TypeError` (wrong type: `"a" + 1`), `KeyError` (missing dict key), `FileNotFoundError`, `ZeroDivisionError`, and so on. If nothing handles it, the program stops and prints a traceback.

`try` / `except` handles it:
```python
try:
    with open(path, encoding="utf-8") as f:
        text = f.read()
except FileNotFoundError:
    text = None
    print(f"no such file: {path}")
```
Python runs the `try` block. If one of the listed exceptions happens, it jumps to the matching `except` block and continues after it; the rest of the `try` block is skipped. If a *different* exception happens, it isn't caught.

Rules worth following from day one:

- **Catch the specific exception you expect.** A bare `except:` catches everything, including your own typos (`NameError`) and Ctrl+C, and hides real bugs.
- **Keep the `try` block small**, around the one line that can fail, so you know what you caught.
- **Decide and record** what bad input becomes. In a data pipeline, count the rejected rows; that number goes in your report.

You can catch several kinds at once, `except (ValueError, TypeError):`, or give each its own `except` block.

## JSON
JSON is the format of web APIs and many data dumps. Its structures map straight onto Python's:

| JSON | Python |
|---|---|
| object `{"a": 1}` | dict |
| array `[1, 2]` | list |
| string `"x"` | str |
| number `1`, `2.5` | int, float |
| `true` / `false` | `True` / `False` |
| `null` | `None` |

```python
import json

with open("loans.json", encoding="utf-8") as f:
    data = json.load(f)                 # the whole file becomes Python dicts and lists
data["members"][0]["name"]              # navigate it like any nested structure

with open("out.json", "w", encoding="utf-8") as f:
    json.dump(data, f, indent=2, ensure_ascii=False)   # pretty, and keeps "è" readable
```
`json.loads(text)` and `json.dumps(obj)` (with an **s**, for *string*) do the same with strings instead of files.

Big dumps are often **JSON Lines**: one complete JSON object per line, not one giant array. Read them line by line, with `json.loads(line)` for each, so memory stays small.

When you first open a JSON file, explore it at the prompt: `type(data)`, `data.keys()`, `len(data["events"])`, `data["events"][0]`. Know its shape before writing code.

## XML
XML stores data as nested **elements**, written with tags. The same record can be stored two ways:
```text
<row id="1" age="39"/>                          values as ATTRIBUTES of the element
<census><id>1</id><age>39</age></census>        values as CHILD ELEMENTS
```
Python's `xml.etree.ElementTree` reads both:
```python
import xml.etree.ElementTree as ET

root = ET.parse("census_row.xml").getroot()    # the whole file as a tree
for el in root.iter("row"):                     # every <row> element, at any depth
    el.attrib                                   # a dict of its attributes: {'id': '1', 'age': '39'}

root = ET.parse("census_elements.xml").getroot()
for el in root.iter("census"):
    el.findtext("age")                          # the text of the child <age>: '39'
    {child.tag: child.text for child in el}     # every child as a dict
```
Special characters are escaped in XML (`<` is written `&lt;`); ElementTree decodes them for you.

`ET.parse` builds the **entire** tree in memory, which is fine for small files and a problem for a multi-gigabyte one. For large files, **stream** with `iterparse`: it hands you each element as soon as its closing tag is read, and you throw it away when you're done with it.
```python
for event, el in ET.iterparse(path, events=("end",)):
    if el.tag == "census":                      # one complete record has been read
        process(el)
        el.clear()                              # free it, so memory doesn't grow
```

## ARFF
ARFF is the format of the Weka tool, and the DSS data comes partly as ARFF. It's a CSV-like data section with a header that describes the columns:
```text
% lines starting with % are comments
@relation sales

@attribute stor_id numeric
@attribute ord_date date 'yyyy-MM-dd'
@attribute payterms {'Net 60','Net 30','ON invoice'}

@data
6380,1994-09-14,'Net 60'
7066,1993-05-24,?
```
- `@relation` names the dataset.
- Each `@attribute` gives a column name and its type. The type can contain spaces (a date format, or a list of allowed values in braces), so split the line into at most three parts: `line.split(maxsplit=2)`.
- After `@data`, each line is one row. Text values may be wrapped in **single** quotes, and `?` means missing.
- Keywords are case-insensitive: `@DATA` is the same as `@data`.

Since the data lines are CSV with single quotes, you don't parse them by hand: `csv.reader(lines, quotechar="'", skipinitialspace=True)` handles quotes and commas inside values.

Real ARFF files are messier than the clean examples: mixed quote styles, apostrophes and commas inside text. When you write a parser, write tests with the nastiest rows you can imagine. Your test file is your proof that the parser works.

## Putting it together
A reader for any format should end up in the same place:
```python
rows = read_csv_rows("a.csv")              # [{'id': '1', ...}, ...]
rows = parse_arff("a.arff")["rows"]        # [{'id': '1', ...}, ...]
rows = xml_attribute_rows("a.xml")         # [{'id': '1', ...}, ...]
```
After that, cleaning, counting and loading are the same code for all of them. That's the payoff of choosing one shape.

> **Remember**
> - `with open(path, encoding="utf-8")`, every time. Add `newline=""` for CSV.
> - Never split CSV lines by hand; the `csv` module handles quotes and commas.
> - Values from CSV, XML and ARFF are strings. Convert on purpose, and turn `""`, `"?"` into `None`.
